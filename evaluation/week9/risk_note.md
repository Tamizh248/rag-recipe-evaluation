# Week 9 — Supply-Chain Risk Note: `ingredient_db_server`

1. **Who wrote it:** the content team, not this codebase's owners — it runs code and data (`mcp_servers/ingredient_db_server.py`'s ingredient table) this project never reviewed as its own, and any update to it ships without this repo's review or tests.
2. **What it can reach:** nothing beyond its own process today (no network calls, no filesystem access outside its source file, no shared credentials) — but it runs inside the agent's trust boundary and receives every ingredient name the agent sends it, which can leak the user's query content (diet, allergy, recipe) even though this server never asked for that context directly.
3. **What it logs:** unknown from the outside — this stand-in logs nothing, but a real third-party server is opaque; every `tools/call` argument (here, ingredient names, which can imply a user's health/allergy profile) should be assumed logged somewhere the content team controls, not us.
4. **What a stolen token could do:** currently nothing, since this server needs no auth token (stdio, spawned locally) — but the moment this becomes a real hosted service reached over HTTP with an API key, a stolen key exposes only ingredient lookups today, and MORE if this server is ever given a `write` or `publish` capability it doesn't have now.
5. **Ship or don't:** ship for read-only ingredient/nutrition lookups, scoped exactly as `lookup_ingredient` is now (one function, no side effects); do not extend its trust without re-reviewing this note, and do not let it hold an allergen-safety opinion the agent trusts unchecked — `get_allergen_profile` (our own server) stays the source of truth for anything allergen-safety-critical.
